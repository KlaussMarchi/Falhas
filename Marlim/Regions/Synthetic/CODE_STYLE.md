# Code Style — Klauss Marchi

> How to write — and how to reorganize — code in the style of Klauss Marchi, in any language. Written for an AI that
> receives a notebook, a module or a firmware tree, often generated by another AI, and must return the same program
> clean. Each section states a principle, then the rules, then real code from Klauss's projects: **Before** shows what
> to undo (most of it from AI-written parts of those projects), **After** shows the target. When a case is not covered,
> derive the answer from the principle, never from the absence of a rule. When two rules pull apart, the order is:
> behavior first, then the structure the project already has, then this document.
>
> Jupyter notebooks are the most frequent target and where generated code fails most — §10 is the longest section for
> that reason. Self-contained: nothing here requires reading another file.

---

## 0. The job

You receive code that works but reads badly — too long, repeated, over-commented, wrapped in defenses, split into
pieces nobody needed — and you return the same program in this style.

**Behavior does not change.** Same inputs, same files written, same numbers, same tables, same information in every
chart. The form changes, and what disappears is only what never ran or never mattered. An obvious typo in a name or a
message may be fixed; a logic bug is reported, never silently fixed.

1. **Read everything before touching anything:** the whole notebook or file, the modules it imports, the files it reads
   and writes, and the neighboring code that already follows this style — the reference for what this document leaves open.
2. **Map it.** For each cell or function: what it needs, what it produces, who uses the result. Mark what is dead (never
   read, never called), what is duplicated (equal except for values) and every signature of generated code (§14).
3. **Decide the shape before editing** (§5, §6): what becomes a class, a function, a table of data, or stays linear;
   what moves to a module because more than one notebook uses it.
4. **Rewrite** following §1–§13. Keep every name another file imports; if renaming is part of the job, update every caller.
5. **Verify.** Run what is cheap — the notebook from the top, the script, the compiler — and compare with the original.
   Never re-run a long training or a cell that needs hardware without asking; say which cells were not executed. Never
   type an output by hand.
6. **Report in Portuguese, briefly:** what changed in structure, what was deleted and why, how behavior was checked, and
   what looked wrong but was left as it was.

## 1. Think first, reuse before creating

An AI writes several times more code than a problem needs, for three reasons: it treats each request as new, so it
duplicates instead of reusing; it wraps everything in handling for errors nothing will raise; and it builds
abstractions for a second case that never comes. A person who knows the codebase writes the one direct path, reuses
what is there, and stops.

Before writing anything:

1. **Does this already exist here?** A helper, a class, a module, a pattern already in the project.
2. **What is the direct path?** The formulation a reader understands on the first pass.
3. **What did I add that nobody asked for?** A flag, a layer, a parameter with one real value, a check for a case that cannot happen.
4. **Does it survive reality?** Empty input, one element, absent device, first iteration.

**Small is not the goal — thinking first is.** There is no line budget; a training pipeline or a whole device may need a
lot of code, and that is right. What separates the two cases is never the size:

| Big because it was not thought through | Big because the problem is big |
|---|---|
| dead code: an unused import, a variable never read, a function never called | every piece is reached |
| conditions and loops stacked deep instead of one direct formulation | the depth mirrors the real structure |
| blocks identical except for constants | each block does a different thing |
| error handling around code that cannot fail | error handling where IO actually fails |
| a parameter, flag or layer with a single real use | every knob is used |

## 2. Comments

A comment carries what the code cannot say: what a class stands for, why a function exists, the physical or
statistical constraint behind a number. **The default is no comment** — across Klauss's own code, hundreds of functions
carry none.

**Above a definition — one line, UPPERCASE, in Portuguese, immediately above it:**
- above **every class**, saying what it represents or what it is for;
- above a **function or method whose name does not say why it exists** or which rule it follows — a statistical test,
  a protocol step, a non-obvious algorithm.

Nothing above `__init__`, above a method of the standard vocabulary (§4) doing its usual job, or above a function whose
name is the whole story (`getFiles`, `setFolder`, `normalizeTable`, `loadModel`). Never two lines, never a block.

**At the end of a line — a short UPPERCASE mark** for a value or a line whose purpose the code cannot show: a
threshold, a count, the origin of an offset, what a branch is waiting for. A unit keeps its spelling (`# ms`, `# mg/L`).

```python
# CURVA a·b^(cx+d) COM DESCARTE DE RÉPLICAS POR GRUBBS
class Calibration:
    ALPHA   = 0.05
    MIN_N   = 4       # CURVE_FIT AJUSTA 4 COEFICIENTES
    MIN_DEV = 0.03    # P90 DA DISPERSÃO DENTRO DOS NÍVEIS

    def __init__(self, xData, yData):
        self.xData = np.asarray(xData, dtype=float)
        self.yData = np.asarray(yData, dtype=float)

    def update(self):
        ...

    # CRÍTICO DE COCHRAN DERIVADO DA DISTRIBUIÇÃO F
    def getCochran(self, k, n):
        ...
```

**Never:** docstrings; comment blocks; banners (`# ====`, `# ────`, `# --- ENCODER ---`); narration of the next line or
numbered steps (`# calcular loss`, `# 2. Derivada do quaternion`); comments addressed to the reader (`# ← ajuste aqui`,
`# como no seu original`, `⚠ ver AVISO`); commented-out blocks of old code; emoji and arrows. In a notebook the
explanation of a step belongs to the markdown cell above it (§10), not to comments inside the code.

## 3. Names

The spelling of a name follows who owns the concept, so a reader always knows where it came from:

| The concept is | Spelling | Examples |
|---|---|---|
| Klauss's, invented in the project | `camelCase` for variables, functions, methods, attributes, parameters | `xData`, `trainLoader`, `stepSize`, `sensorValue`, `getSettlingTime`, `loadModel` |
| a library's — a kwarg passed through, a method the library calls, a key it defines | the library's own spelling | `forward`, `__getitem__`, `test_size`, `n_iter`, `img_size`, `num_filters`, `restore_best` |
| the field's — control, signals, physics, statistics | the notation as written on paper | `G_ma`, `G_feedback`, `s_d`, `e_ss`, `Ts`, `Wn`, `zeta`, `f_c`, `w_c`, `Xn1`, `Yn2`, `A_bb`, `Ahat`, `mu`, `sigma`, `dt` |

Mixing them in one signature is correct: `RandomSearch(model, params, xData, yData, k=5, test_size=0.20, n_iter=10)`.
Never translate field notation into prose (`f_c`, not `cutoffFrequency`).

- **Structure:** types and component folders `PascalCase` (`CrossValidation`, `Metrics/ROC/`); tunable and data-derived
  constants `UPPER_SNAKE_CASE` (`TARGET`, `K_CV`, `N_STATES`, `OFFSET`, `ALPHA`, `PKT_LEN`); a lookup table is
  `UPPER_SNAKE_CASE` at module or notebook level (`STATS`, `LEVELS`) and a lowercase noun when declared on a class
  (`options`, `scoring`, `student`); keys written to JSON or CSV `snake_case` (`'train_loss'`, `'val_iou'`, `'img_path'`).
- **Short, and named for the content:** `df`, `ref`, `ix`, `n`, `k`, `row`, `path`, `folder`, `output`, `values`,
  `target`, `info`, `results`. Never `concentrationValue`, `calculatedMeanResult`, `df2`, `newDF`, `df_new`, `temp_df`
  — a second table is named for what it holds (`levels`, `history`, `components`).
- **Recurring data reuses the same names**, so every notebook reads the same: `df`, `xData`/`yData`,
  `xTrain`/`xTest`/`yTrain`/`yTest`, `yPred`, `yModel`, `yProba`, `TARGET`, `K_CV`, `N_STATES`, `OPTIONS`, `model`,
  `params`, `selector`, `search`, `cross`, `analyser`, `network`, `trainer`, `history`, `results`.
- **Never a leading underscore** (`_getFeatures`, `_Fc`, `self._initialized`). Something used once is inlined in its
  caller; something used more than once is an ordinary public member.
- **Language:** identifiers in English, always (`getPhaseVariables`, not `getVariaveisFase`). Comments, markdown, chart
  titles, messages to a person, commits and reports in Portuguese; a firmware log follows the language that firmware
  already uses.

## 4. One vocabulary, everywhere

The same verbs in every class and every language, so a reader learns the API once and knows what an unseen type does:

| Verb | Meaning |
|---|---|
| `update()` | advances the object's state: the heavy computation that fills public attributes, or one step of a recurrence that returns the new output |
| `get()` / `getX()` · `set()` / `setX()` | read the main value or a derived one · write |
| `info()` | summary as a dict, ready for `pd.DataFrame([...])` or JSON |
| `print()` | the same summary printed; may return the table for display |
| `plot()` · `showX()` · `display()` | the object's chart · one specific view (a panel, a tile, the unique values) · tables in a notebook |
| `process()` | intermediate transform used inside `update()` |
| `apply()` | use on new data what `update()` fitted |
| `evaluate()` | score the best candidate of a search or a training |
| `compute()` | one output sample of a filter or difference equation from its stored states |
| `setup()` · `handle()` | one-time initialization · body of the continuous loop |
| `ready()` · `check()` · `reset()` | predicate that may act (a timer that rearms) · verification that acts · back to the initial state |
| `connect()` · `send()` · `listen()` · `read()` | IO |
| `start()` · `stop()` | a long process and its end |
| `save()` · `load()` · `export()` | persistence |

No synonyms for these meanings: not `run`, `execute`, `calculate`, `perform`, `process_data`, `do_training`,
`generate_report`.

**Construction only stores** what it receives and derives cheap attributes; the work — fitting, searching, reading
files, training, drawing — happens in `update()`, `start()` or `plot()`, called by the owner of the object. A constructor
that ends in `self.update()` or draws a chart hides the cost where nobody expects it (`nn.Module.__init__` declares
layers because the library requires it).

```python
cross    = CrossValidation(model, xData, yData, K_CV)
analyser = GaussianAnalyser(cross)
analyser.update()
analyser.plot()
analyser.info()
```

## 5. The shape follows the state

The structure mirrors the data, not the ambition of the design.

- **State that survives the call and is read by more than one operation → a class.** `Correlations(df)` with `get`,
  `plot` and `heatmap`; `Calibration(xData, yData)` with `update`, `apply`, `table`, `info` and `plot`.
- **Functions that all receive the same data to answer different questions about it are a class that was never
  written** — that data is its state, and a flag that switches between returning and printing is two methods. A
  transform that returns new data stays a function.
- **No surviving state → a function:** a transform, a calculation, a plot helper (`normalizeTable(df, key, dt)`,
  `getStates(df, key, var, n)`, `getFiles(path)`).
- **A linear script stays linear:** an acquisition loop or a runner is imports, constants, the few definitions it needs,
  and the flow at the bottom.

**Before** — the same functions pasted into every control notebook:
```python
def getOvershoot(time, response): ...
def getPeakTime(time, response): ...
def getSettlingTime(time, response, tolerance=0.02): ...
def getAllInfo(time, response, show=True, setpoint=1): ...
```
**After** — one class in `StepResponse/index.py`, imported by every notebook:
```python
# MÉTRICAS DA RESPOSTA AO DEGRAU DE UM SISTEMA SIMULADO
class StepResponse:
    TOLERANCE = 0.02    # FAIXA DO CRITÉRIO DE ASSENTAMENTO

    def __init__(self, time, response, setpoint=1):
        self.time     = np.asarray(time)
        self.response = np.asarray(response)
        self.setpoint = setpoint

    def update(self):
        ...

    def info(self):
        ...

    def print(self):
        ...
```
```python
step = StepResponse(time, response)
step.update()
step.info()
```

Signs that a class did not earn its existence: it is built once and discarded after one call; its constructor does all
the work and nothing else exists (`Plotter(metrics)` drawing inside `__init__` → a function `plotMetrics(metrics, limits, title)`);
its methods never read what another method wrote; it only groups helpers, which is what a module is for.

**Long is not the problem.** A flat dispatch of sequential conditions, a menu of options, a block of layer declarations,
a protocol with many commands are correct as they are. Long because two responsibilities merged → split by
responsibility, never by extracting a private helper that only moves lines around.

**Where code lives.** A definition used by one notebook stays in it, in the cell of its step. Used by two or more
notebooks of the same study → a folder module beside them, with the same API (§11). Each study keeps its own copy of its
modules; there is no package shared across projects.

Never: an abstract base with one implementation, a family of subclasses that differ only in parameters, deep inheritance
where composition works, accessors that only forward a field, a configuration file for what fits as data on the class.

## 6. Difference becomes data

When pieces of code differ only in values, the difference is data, not code. This is the most valuable move available
and the one generated code misses most.

A menu of variants is a table on the class, and the variant is picked by lookup:
```python
# MENU DE MODELOS COM O ESPAÇO DE BUSCA DE CADA UM
class ModelSelector:
    options = {
        'logistic_regression': {
            'model': LogisticRegression(random_state=42),
            'params': {'C': loguniform(1e-4, 1e2), 'penalty': ['l1', 'l2']}
        },
        'random_forest': {
            'model': RandomForestClassifier(random_state=42),
            'params': {'n_estimators': randint(100, 600), 'max_depth': randint(5, 50)}
        }
    }

    def __init__(self, name):
        self.chosen   = name
        self.selected = self.options[name]

    def get(self):
        model  = Pipeline([('scaler', StandardScaler()), ('model', self.selected['model'])])
        params = {f'model__{key}': value for key, value in self.selected['params'].items()}
        return model, params
```

Repeated computations become a table and one comprehension, defined once where every notebook can import it.

**Before** — and pasted again into `3 - Compare.ipynb` for a new sample:
```python
df['mean']      = [np.mean(data) for data in df.data]
df['std']       = [np.std(data, ddof=1) for data in df.data]
df['min']       = [np.min(data) for data in df.data]
df['mean_diff'] = [np.mean(np.gradient(data)) for data in df.data]
df['std_diff']  = [np.std(np.gradient(data), ddof=1) for data in df.data]
df['min_diff']  = [np.min(np.gradient(data)) for data in df.data]
```
**After:**
```python
STATS = {
    'mean': np.mean,
    'std': lambda x: np.std(x, ddof=1),
    'min': np.min
}


def getFeatures(data):
    diff = np.gradient(data)
    return {**{key: fn(data) for key, fn in STATS.items()}, **{f'{key}_diff': fn(diff) for key, fn in STATS.items()}}


df = df.join(pd.DataFrame([getFeatures(data) for data in df.data], index=df.index))
df.head(3)
```

A choice between variants is a sequence of conditions each returning its result, a lookup, or an aligned conditional
chain — never an `elif` chain:
```cpp
channel = (channel == 1)  ? 6  :
          (channel == 6)  ? 3  :
          (channel == 3)  ? 11 :
          (channel == 11) ? 2  : 1;
```

A loop over elements is an operation on the whole array:

**Before:**
```python
for i in range(self.size - 1, 0, -1):
    self.buffer[i] = self.buffer[i - 1]
```
**After:**
```python
self.buffer[1:] = self.buffer[:-1].copy()
```

**Fewer lines through better logic, never through compression.** Statements share a line only when they form one
logical unit — `plt.xlabel('time'); plt.ylabel('sensor'); plt.grid()`, `Xn2 = Xn1; Xn1 = Xn;`, `model.plot(); plt.show()`.
Unrelated statements glued together are not concise, they are unreadable:
```python
features_list = []; values_list = []; left_list = []; right_list = []; tree_roots = []
L = tree.tree_.children_left; R = tree.tree_.children_right
```

## 7. Layout

Code that looks like one hand wrote it is read faster than code that is merely correct.

**A call is never broken across lines.** Its arguments stay on the line of the call, however many there are. When the
line stops reading as one unit — there is no fixed column; judge it by this example — the arguments are partitioned into
named, aligned variables first, and the call stays on one line.

**Wrong** — the call broken:
```python
response = requests.post('http://localhost:8000/score', json=info,
                timeout=5, best=4, data={'key': 'value'},
         headers={'Content-Type': 'application/json'})
```
**Right** — one line:
```python
response = requests.post('http://localhost:8000/score', json=info, timeout=5, best=4, data={'key': 'value'}, headers={'Content-Type': 'application/json'})
```
**Right** — too big, so partitioned:
```python
data    = {'key': 'value', 'another_key': 'another_value'}
headers = {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer <token>',
    'worst': {'name': 'klauss', 'info': [1, 3.3333, 3, 4, 5.34, 'ok'], 'description': {'label': 'ok', 'value': 1.0}}
}

response = requests.post('http://localhost:8000/score', json=info, timeout=5, best=4, data=data, headers=headers)
```

The same move removes repeated calls:

**Before:**
```python
trainLoader = DataLoader(
    trainDataset,
    batch_size=BATCH_SIZE,
    shuffle=True,
    num_workers=NUM_WORKERS,
    pin_memory=True if torch.cuda.is_available() else False
)

valLoader = DataLoader(
    valDataset,
    batch_size=BATCH_SIZE,
    shuffle=False,
    num_workers=NUM_WORKERS,
    pin_memory=True if torch.cuda.is_available() else False
)
```
**After:**
```python
loaderOptions = {'batch_size': BATCH_SIZE, 'num_workers': NUM_WORKERS, 'pin_memory': torch.cuda.is_available()}

trainLoader = DataLoader(trainDataset, shuffle=True, **loaderOptions)
valLoader   = DataLoader(valDataset, shuffle=False, **loaderOptions)
```

- **Multi-line is for literals that are data** — a nested dict, a list of records, a matrix whose rows are visual rows —
  with one entry per line and keys not padded. A method chain is never spread over lines either: name the intermediate.
```python
results = {
    'model': selector.chosen,
    'params': {key: str(value) for key, value in model.get_params().items()},
    'K_CV': K_CV,
    'info': analyser.info(),
    'variables': xData.columns.tolist()
}
```
- **Alignment.** Consecutive related assignments align on `=`; the next block starts its own alignment.
```python
df     = pd.read_csv('../Dataset/model.csv')
TARGET = 'alcohol'
K_CV   = 5
```
- **Guards and conditions.** Each case is its own `if`, the body on the next line, a blank line after it; no `elif`
  chain, no `else` after a `return`. A two-way choice is one line (`x = 3 if getInfo(x) is not None else 0`); a chained
  conditional in C/C++ aligns conditions and results in columns.
```python
def getInfo(x):
    if x is None:
        return None

    if x > 3:
        return {'status': 'success', 'value': x}

    return -1
```
```cpp
const char* msg = device->test.had_alcohol        ? lang.lastAlcoholTest.get() :
                  device->test.postpone.allowed() ? lang.touchToPostpone.get() : lang.postponeLimitExceeded.get();
```
- **Blank lines.** One between logical blocks inside a body and between methods; never two inside a body; two between
  the definitions and the code that uses them — in a notebook cell, a module or a script.
- **Member order** is the same in every type, so any class is scanned the same way: class-level tables and constants →
  construction → `update()` and core operations → business logic → getters and `info()` → visual output (`print`,
  `plot`, `show*`, `display`) → transformation (`apply`) → persistence (`save`, `load`).
- **Python strings and imports.** Single quotes, double only when the text holds a single quote; f-strings for
  formatting. Imports at the top of the file or of the notebook section, related standard modules on one line
  (`import json, os, joblib, math`), none unused or duplicated.

## 8. Robustness is a shape, not a wrapper

Reliability comes from how the code is arranged, not from wrapping it in exception handling.

**Each failure mode gets its own guard that returns nothing meaningful; the caller decides.**
```python
def get(self):
    if self.device.in_waiting == 0:
        return None

    try:
        line = self.device.readline().decode('utf-8')
    except (serial.SerialException, UnicodeDecodeError):
        return None

    return line.strip() if line else None
```
```python
while True:
    values = device.getList()

    if values is None:
        continue

    alcohol = getFirstDigit(input('alcool: ').strip())
    df      = pd.concat([df, pd.DataFrame([{'data': values, 'alcohol': bool(alcohol)}])])
    df.to_csv(TABLE_PATH, index=False)
```

- **Error handling belongs where errors happen** — a device, a socket, a file chosen by a person — with named exceptions
  and a cleanup that always runs. Never `except:` or `except Exception` around arithmetic, pandas or plotting; never a
  `try` whose branches do the same thing.
- **Fail soft on data, loud on setup.** A corrupt packet or a sensor with too few points is skipped and the loop goes on.
  A missing model file, a port that does not open, too few valid points to fit a curve stop with a clear message:
  `raise ValueError(f'{n} pontos válidos: calibração incompleta, mínimo de {self.MIN_N}')`.
- **Cleanup is idempotent.** Stopping twice, or resetting before starting, is never an error.
- **The physical world lives in named constants** — baud rates, timeouts, packet lengths, sampling periods, cutoffs,
  thresholds, patience (`CMD_MIN_SIZE`, `PKT_LEN`, `MIN_N`, `TOLERANCE`) — never a literal buried in logic. A function
  whose whole body is a table of values is where those values live. Real hardware drifts; the tuning knob stays even
  when everything else is minimal.

A check that prints an error and lets the code run into a crash is the worst of both:

**Before:**
```python
if not os.path.exists(baseDir):
    print(f"Error: Model {modelId} not found at {baseDir}")
```
**After:** nothing — `open(f'{baseDir}/info.json')` on the next line already fails with the path in the message.

**Simulate before delivering**, and say which cases were checked: empty input, one element, zero variance, the device
absent or sending half a message, the first iteration with state still unset, values at and just past the limits, the
same call twice or out of order.

## 9. Nothing speculative

Every abstraction, parameter, flag and layer needs a user that exists today. "It might be useful later" is how code
becomes unmaintainable; later can add it in less time than it costs to carry it now. Deleting is worth more than adding:
`argparse` for a value that never changes, a `main()` wrapper around a linear script, logging configuration in a
notebook, a registry for two variants, an empty stub class, a function nobody calls — all go.

The exception is the safety net: validation at a real trust boundary (a device, a network, a file chosen by a person),
handling that prevents data loss, and the calibration knob of a physical system.

## 10. Notebooks

A notebook is an experiment report that runs: read top to bottom, it shows each step, the theory behind it when there
is one, and the result right below. Generated notebooks fail here more than anywhere — prose headers, cells that show
nothing, a whole pipeline in one cell, prints everywhere, the same helpers pasted into every notebook.

**A study is a numbered pipeline whose notebooks exchange files, never variables:**
```text
Alcohol/
├── Aquisition/index.py          serial acquisition, appends to Dataset/target.csv
├── Dataset/                     target.csv, model.csv
└── Model/
    ├── 1 - Processing.ipynb     target.csv  -> cleaning and features -> model.csv
    ├── 2 - Model.ipynb          model.csv   -> search, validation, final fit -> Backup/model_N/
    ├── 3 - Compare.ipynb        Backup/*/info.json -> ranking, best model, export to firmware
    ├── Backup/model_N/          info.json, model.pkl
    ├── Selector/index.py
    ├── RandomSearch/index.py
    └── Metrics/CrossValidation/index.py
```
A notebook with a single job is named for it (`Analysis.ipynb`, `Format.ipynb`, `Predict.ipynb`). Parameters shared by
several notebooks live in a JSON (`info.json`) read into `OPTIONS`.

**Top of the notebook.**
- The first cell holds the imports of the libraries used throughout and the global display settings
  (`pd.set_option('display.max_columns', None)`), and nothing else.
- Then configuration and data, with the constants that depend on them right after the load — aligned,
  `UPPER_SNAKE_CASE` — ending with the data on screen (`df.head(3)`, `OPTIONS`).

**Sections.**
- **The markdown cell is the section header:** `# UPPERCASE IN PORTUGUESE` for a section, `### ...` for a subsection,
  `#### ...` for a check inside it — `# EXTRAINDO DADOS`, `# SELECIONANDO MODELO`, `# AVALIAÇÃO GAUSSIANA`,
  `# SALVANDO O MODELO`, `### VALORES ÚNICOS`, `#### TESTE NUMÉRICO`.
- Below the header, only when the step needs it: `- ` bullets in Portuguese stating the fact or the theory, formulas in
  LaTeX (`$...$`, `$$...$$`, `$\Rightarrow$`), **bold** for a named concept. Theory comes before the code that applies it.
- Never "Passo 1", emoji, "Neste notebook vamos...", a summary of what the code will do, horizontal rules, or a banner
  comment inside a code cell.
- A library or module used by one section only is imported in a small cell right after that section's header.

**Cells.**
- **One cell, one step** — the unit whose result you want to see before moving on: load, inspect, transform, fit, plot,
  save. Not one line per cell, not a pipeline in one cell.
- **Every working cell ends with visible proof:** the object as the last bare expression (`df`, `df.head(3)`, `model`,
  `coefs`, `results`, `(zeta, Wn, s_d)`), `display(...)` when there is more than one table, a chart, or one short
  `print` of a scalar result. A cell that saves ends showing what it saved.
- **Silent cells exist only for imports and for a definition used by later cells.**
- The flow of a notebook is linear code in its cells — never wrapped in a `main()`, a `Pipeline` class or a function
  called once at the bottom. Paths are relative to the notebook (`../Dataset/model.csv`, `Backup/model_3/info.json`).
- A function or class used right away is defined in the cell that uses it, and the use follows after two blank lines:

## 11. Python modules and scripts

**Folder as module.** A reusable class lives in `Name/index.py`, exports one main type named after the folder, and is
imported as `from Name.index import Name`; related modules are grouped under one folder (`Metrics/CrossValidation/index.py`,
`Metrics/ROC/index.py`). Importing a module never runs work.

```python
import numpy as np
import pandas as pd
from sklearn.base import clone
from sklearn.model_selection import StratifiedKFold, cross_validate


# VALIDAÇÃO CRUZADA ESTRATIFICADA COM MÉDIA E DESVIO DE CADA MÉTRICA
class CrossValidation:
    scoring = {'accuracy': 'accuracy', 'precision': 'precision_weighted', 'recall': 'recall_weighted', 'roc_auc': 'roc_auc_ovr_weighted'}

    def __init__(self, model, xData, yData, k=4, seed=42):
        self.model = clone(model)
        self.xData = xData
        self.yData = yData
        self.seed  = seed
        self.k     = k

    def update(self):
        self.cv     = StratifiedKFold(n_splits=self.k, shuffle=True, random_state=self.seed)
        result      = cross_validate(self.model, self.xData, self.yData, cv=self.cv, scoring=self.scoring)
        self.scores = [self.process(result, key) for key in self.scoring]
        self.df     = pd.DataFrame(self.scores)

    def process(self, result, key):
        values = result[f'test_{key}']
        return {'name': key, 'values': values, 'mean': np.mean(values), 'std': np.std(values)}

    def info(self):
        return {score['name']: float(score['mean']) for score in self.scores}

    def print(self):
        for score in self.scores:
            print(f"{score['name'].upper()}: {score['mean']*100:.3f}% (±{score['std']*100:.2f}%)")

        return self.df
```

## 12. Embedded (ESP32 / Arduino)

- **The file tree mirrors the device:** every component is a folder whose entry point is `index.h`, a subcomponent is a
  subfolder (`device/`, `objects/sensors/Kernel/`, `objects/telemetry/serial/`, `utils/text/`). Header-only, with an
  include guard (`#ifndef SERIAL_H`); a `.cpp` only where an interrupt or a static member forces it.
- **`Main.ino` only wires:** includes the device, instantiates it (`Device device{"v1.0.7"};`), sets behavior flags in
  `setup()` before `device.setup()`, and delegates `loop()` (`device.tasks.handle();`).
- **A component receives its parent by template pointer** and reaches siblings through it — no singletons, no globals.
- **Every component has `setup()` and `handle()`**, and the parent propagates both.
- **Rate limiting uses a static timer inside the method** that needs it: `static Listener timer = Listener(dt);` then
  `if(!active || !timer.ready())` / `return;` — or, on a bare Arduino, `static unsigned long startTime;` and
  `if(millis() - startTime < INTERVAL)` / `return step;`.
- **Members are public by default**, with behavior flags (`enabled`, `debug`, `multitask`) checked by a guard at the top
  of `setup()` and `handle()`. In a `void` function a guard that acts returns the call: `return leds.duty1.set(500, 500);`.
- **A command protocol is a flat sequence** of `if(command.contains("..."))` blocks, each ending in `return`.
- **Constants:** protocol, mode and pin constants grouped by prefix in `globals/constants.h` and aligned
  (`#define HR_MODE 0`, `#define JSON_PROTOCOL 0`, `#define SENSOR_PIN   A0`); constants of one type stay on the type
  (`static const int PKT_LEN = 60;`).
- **A stored member is a fixed buffer** (`Text<64> response;`), never a `String`; as a local or a return value a
  `String` is fine.
- **Layout:** `void setup(){` with no space before the brace; `if(cond)` and `for(int x=0; x<SIZE; x++)` with no space
  after the keyword; a single-statement body on the next line without braces; `5*60*1000`; access specifiers indented
  two spaces and members one tab; constructor initializers one per line ending in `{}`.
- Near-identical packet parsers or branches that differ only in offsets, lengths and scales are one routine and a table (§6).
